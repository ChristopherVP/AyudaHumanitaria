# 🚚 Humanitarian Aid Distribution System

**A decision-support desktop application that plans humanitarian aid across continental Ecuador: which communities to help first, how much each collection center can send, which vehicles go out, in what order they visit the communities and when each trip leaves and returns.**

*Sistema Inteligente de Distribución de Ayuda Humanitaria* is a **Java SE (Maven) + Swing** application created as an **integrative project** at the Universidad Central del Ecuador. It manages **collection centers, communities and vehicles** (full CRUD on a **PostgreSQL** database through **JDBC**), shows everything on a **map of Ecuador**, builds **dated distribution plans** with the five classic algorithm-design techniques (Divide and Conquer, Greedy, Dynamic Programming, Backtracking, Branch and Bound) and exports **Excel** and **PDF** reports.

> The first time it runs against an empty database, the app creates the tables and loads sample data (5 centers, 32 communities and 13 vehicles), so every feature can be tried immediately. Afterwards, everything you create stays in the database and nothing is loaded twice.

## ✨ Features at a Glance

- **Interactive map of Ecuador** with switchable layers (road network, cities, communities, names, coverage per center, active routes) and export to **PNG**.
- **Collection centers** — register, edit, delete, search, restock and pick the location **on the map** (city and province are derived automatically from the coordinates).
- **Communities** — full CRUD with map location, the center that serves each one and delivery progress (planned vs. delivered tons).
- **Vehicles** — full CRUD; every vehicle belongs to a center and shows whether it is on a trip.
- **Logistics tab**
  - **Automatic plan:** the algorithms choose vehicles, centers, loads and routes.
  - **Manual plan:** you choose which vehicles leave and how many trips each makes, optionally with a Greedy suggestion.
  - **Quick simulation** (departure in 30 minutes), **confirm** and **cancel** plans, and a **history** of plans and trips.
  - Real **schedules**: departure, arrival at each stop, driver rest, return, and trip status computed against the real clock (*Planned → On route → Completed*, or *Cancelled*).
  - A separate **algorithm demonstration** area to run each technique on its own and read the result.
- **Five algorithm-design techniques** working together in the planner, plus **six hand-written sorting algorithms** and **three searching algorithms**.
- **Road study of Ecuador** (main corridors, condition of the state road network per province) used to adjust travel speeds by region.
- **Reports** — six sorted reports, descriptive statistics with automatic conclusions, **Excel** workbook (11 sheets) and **PDF with maps**.
- **PostgreSQL persistence** with transactional saving of plans; automatic table creation; embedded **H2** as a fallback for quick tests.
- **Input validation** with clear Spanish messages and custom exceptions; splash screen; built-in **Help** tab.

## 🔧 Installation and Database Setup

```bash
# 1. Get the project
git clone https://github.com/ChristopherVP/AyudaHumanitaria.git
cd AyudaHumanitaria

# 2. Compile and download dependencies
mvn clean compile
```

### Create the database

The application creates the **tables**, but not the database itself. Create it once (pgAdmin or `psql`):

```sql
CREATE DATABASE "AyudaHumanitaria";
```

### Configure the connection

Create a file named `db.properties` **next to `pom.xml`**:

```properties
DB_URL=jdbc:postgresql://localhost:5432/AyudaHumanitaria
DB_USER=postgres
DB_PASSWORD=your_password
```

- `db.properties` is listed in `.gitignore`, so the password is **never uploaded to GitHub**. Never put credentials in the source code.
- Lookup order for each value: **JVM system property** (`ayudahumanitaria.db.url`, `.user`, `.password`) → **`db.properties`** → **environment variables** (`DB_URL`, `DB_USER`, `DB_PASSWORD`).
- If no `DB_URL` is found anywhere, the app silently falls back to a local **H2** file database (`./data/ayudahumanitaria`).

## ▶️ Running the Application

```bash
mvn exec:java
```

Or run `uce.edu.ec.ayudahumanitaria.ejecutable.Main` from your IDE (the working directory must be the project folder so `db.properties` is found).

On startup, a **splash screen** shows the progress while the app (1) connects and creates any missing tables, (2) loads the sample data only into empty tables and (3) opens the interface. The console prints which database was used:

```text
[BD] Conectado a jdbc:postgresql://localhost:5432/AyudaHumanitaria (base: AyudaHumanitaria)
```

If something fails, a dialog explains the error and the program exits.

## 🧭 How to Use It

The window has seven tabs.

| Tab | What you do there |
|-----|-------------------|
| **Mapa** | See centers, communities, coverage and active routes. Toggle layers, restore the view or save the map as PNG. |
| **Centros** | Register centers (name, address, stock in tons), choose their location on the map, edit, delete, search and **restock**. |
| **Comunidades** | Register communities (inhabitants, priority 1–10, required tons, location on the map). The table shows the serving center and the delivery progress. |
| **Vehículos** | Register vehicles (ID and capacity in kg) and assign them to a center; the table shows whether each one is on a trip. |
| **Logística** | Calculate, review, confirm or cancel distribution plans (automatic or manual) and run each algorithm separately. |
| **Reportes** | Sorted reports, statistics with conclusions, Excel and PDF export. |
| **Ayuda** | Explains the workflow, the rules, the algorithms and how to read the map and the reports. |

### Typical workflow

1. Check or register **centers**, **communities** and **vehicles**.
2. Go to **Logística**, choose the departure date and time, and press **Calculate automatic plan** (or **Quick simulation**).
3. Review the trips, their itineraries and the route drawn on the map. Anything that could not be covered is listed as **pending**, with the reason.
4. Press **Confirm plan**. It is saved in one transaction: the stock of each center is discounted and the vehicles become busy.
5. Use **Update states** to refresh *Planned / On route / Completed* against the real clock. A plan that has not departed can be **cancelled**, which returns the stock to the centers.
6. Generate the **Excel** or **PDF** report from **Reportes**.

## 🧮 How a Distribution Plan Is Built

`PlanificadorDistribucion` receives the data and returns an **immutable** `PlanDistribucion`. It uses no database and no GUI, which makes it easy to test.

1. **Greedy** — each community is assigned to its **nearest center**; each center's stock is shared by **descending priority**.
2. **Divide and Conquer** — finds the community with the greatest benefit in each center.
3. **Dynamic Programming (0/1 knapsack)** — builds the groups of communities that fit in one vehicle, maximizing benefit.
4. **Branch and Bound** — assigns vehicles to groups, minimizing wasted capacity.
5. **Backtracking** — orders the stops of each trip so high-priority communities are reached sooner without lengthening the route too much (weighted by road conditions).

Groups are processed in **waves** to keep the search tree small. Every plan reports how many nodes each algorithm explored and how many branches it pruned.

**Operating assumptions** (`ParametrosSimulacion`, all configurable):

| Parameter | Default |
|-----------|--------:|
| Average speed | 50 km/h (adjusted per region and road condition) |
| Maximum driving per day | 8 h |
| Driver rest | 10 h |
| Unloading time per community | 30 min + 10 min per ton |
| Vehicle preparation between trips | 2 h |
| Maximum stops per trip | 7 |

```text
benefit = inhabitants × priority
```

## 🧠 Algorithms

All of them are implemented from scratch in `dominio/Algoritmos.java` (no library sorting).

| Technique | Where it is used |
|-----------|------------------|
| **Divide and Conquer** | Community with the greatest benefit (recursive halving, O(n)). |
| **Greedy** | Nearest-center assignment, supply distribution by priority, vehicle suggestion (`RecomendadorEnvio`). |
| **Dynamic Programming** | 0/1 knapsack to choose which communities travel together. |
| **Backtracking** | Optimal visiting order (TSP type) with pruning; weighted version for plans. Limited to 8 stops. |
| **Branch and Bound** | Vehicle ↔ group assignment with an upper bound on coverage. |

### Sorting and searching

| Algorithm | Complexity (typical) | Used in |
|-----------|----------------------|---------|
| **Quick sort** | O(n log n) | Default listings, benefit report. |
| **Merge sort** | O(n log n) | Communities by priority. |
| **Insertion sort** | O(n²) | Communities by required resources. |
| **Bubble sort** | O(n²) | Communities by name. |
| **Selection sort** | O(n²) | Vehicles by capacity. |
| **Shell sort** | ~O(n^1.3) | Vehicles by identifier. |
| **Sequential search** | O(n) | Generic search by condition. |
| **Binary search (iterative / recursive)** | O(log n) | Search on sorted arrays. |

All are generic (`<T>` with a `Comparator`), so the same code sorts communities, centers and vehicles.

## 🗺 Geography and Road Study

- **Continental Ecuador only** (Galápagos has no land connection). Every location must fall inside the country and be consistent with its province.
- **Distances** use the haversine formula multiplied by a **road factor of 1.35** (Andean roads are typically 1.2–1.6× the straight line).
- **`EstudioVial`** is a *referential* road study: main corridors (Panamericana E35, coastal E15, Amazon trunk road E45, …), the share of state roads in poor condition per province and the average speed per region. It slows the schedule where roads are worse, and sources are cited in the code.
- ⚠️ It is **not real-time information**. Before dispatching a real trip, check the closures published by the Ministry of Infrastructure and Transport and ECU 911.

### On-screen reports

Communities by **benefit**, **priority**, **required resources** or **name**, and vehicles by **capacity** or **identifier** — each with a different sorting algorithm (see the table above).

Summary, general map of centers, communities and routes, centers, communities and delivery progress, fleet, trips with itineraries, and pending items.

## 🗄 Database

PostgreSQL is accessed through JDBC (`ConexionBD`, configured by `ConfiguracionDB`). The tables are created with `CREATE TABLE IF NOT EXISTS` on every start, so existing data is never touched, and missing columns are added automatically if the tables came from an older version.

```text
CENTRO ──< VEHICULO
   │
   └─────< VIAJE >──── PLAN
              │
              └──< PARADA >── COMUNIDAD
```

| Table | Content |
|-------|---------|
| `centro` | Name, city, province, coordinates, stock (t), address. |
| `comunidad` | Name, province, inhabitants, priority, required tons, coordinates, address. |
| `vehiculo` | ID, capacity (kg), assigned flag, destinations text, center. |
| `plan` | Creation date, departure, log and pending list. |
| `viaje` | Plan, center, vehicle, load, distance, departure, return, status. |
| `parada` | Trip, community, order, tons, km, arrival and departure. |

- Sample data is inserted **only into empty tables**, so restarting or rebuilding the project never duplicates it.
- Plans are saved and cancelled inside a **single transaction** (commit or rollback).
- All queries use `PreparedStatement`. Passwords are never printed (`ConfiguracionDB.toString()` omits them).

## ✅ Validation Rules

| Field | Rule |
|-------|------|
| Names | Letters, numbers and common punctuation; up to 100 characters. |
| Address | Required; 5 to 150 characters. |
| Inhabitants | 1 to 2,000,000. |
| Priority | Integer from 1 to 10. |
| Required resources | 0.1 to 5,000 t. |
| Vehicle capacity | 500 to 40,000 kg. |
| Vehicle ID | 2–15 characters: letters, numbers and hyphen (stored in capitals, e.g. `UIO-001`). |
| Center stock | Up to 1,000,000 t; it can never go below zero. |
| Location | Inside continental Ecuador and consistent with the province. |
| Departure | Not in the past and not more than one year ahead. |
| Delete / edit | A center, vehicle or community with planned or on-route trips cannot be deleted; required tons cannot drop below what is already committed. |

Validation errors use `ValidationException` and database errors use `PersistenciaException`; both carry readable messages to the interface.

## 🏗 Architecture and Design Notes

```text
 GUI (Swing panels) ──► Managers (dominio) ──► DAO (persistencia) ──► PostgreSQL (JDBC)
         │                     │
         │                     └──► Planner / Algoritmos / geo (pure logic, no GUI, no DB)
         └──► Excel / PDF exporters
```

- **MVC with a persistence layer:** the domain knows nothing about Swing; only `persistencia` touches SQL.
- **Managers** validate and apply business rules before delegating to the DAOs.
- **Pure, testable planner:** `PlanificadorDistribucion` and `GeoEcuador` take data in and return immutable results.
- **Responsive startup:** database initialization runs in a `SwingWorker` while the splash screen animates.
- **Portable SQL:** queries avoid vendor-specific functions so the same DAOs run on PostgreSQL and H2.
- **Clean shutdown:** a JVM shutdown hook closes the connection.

## ⚠️ Assumptions and Limitations

This is an **educational project**, not an operational logistics system.

- The road study and travel speeds are **referential estimates**, not live traffic or closures.
- Distances are straight-line distances scaled by a road factor, not routes from a mapping service.
- A trip has at most **7 stops** (Backtracking grows factorially); the stand-alone route demo is limited to 8.
- Capacities are compared in tons; vehicles are entered in kg and converted.
- Greedy decisions favor priority and do not guarantee the maximum total benefit.
- The application has no automated test suite yet.
- The interface, reports and messages are in **Spanish**; there is no web or command-line version.

## 🛠 Troubleshooting

| Problem | Solution |
|---------|----------|
| `release version 17 not supported` | Install JDK 17+ and point `JAVA_HOME` to it (`java -version`, `mvn -v`). |
| `mvn` is not recognized | Install Maven and add it to `PATH`, or run the project from your IDE. |
| “No se pudo conectar a PostgreSQL” | Check that the server is running and that `DB_URL`, `DB_USER` and `DB_PASSWORD` in `db.properties` are correct. |
| `database "AyudaHumanitaria" does not exist` | Create it first: `CREATE DATABASE "AyudaHumanitaria";`. |
| The data is not in the database I expect | Read the console line `[BD] Conectado a …`. If it shows H2, `db.properties` was not found: run from the project folder. |
| “Error crítico” dialog on startup | The message explains the cause (connection, permissions, locked H2 folder). |
| Sample data appears again | Only if a table was emptied by hand; the loader fills **empty** tables only. |
| Excel / PDF cannot be saved | The file is open in another program or the folder is read-only; close it or choose another location. |
